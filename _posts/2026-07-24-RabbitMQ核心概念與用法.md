RabbitMQ：**message broker（訊息代理）**，居中轉發訊息，讓送訊息與收訊息的程式不用互相認識。用途：**解耦**、**非同步**（送出不等對方處理完）、**削峰**（流量暴增先排隊）。

## 核心概念與訊息流

```
  publish(routing_key)        比對 Binding              deliver
Producer --------------> Exchange ----------> Queue ----------> Consumer
                            |                   |                  |
                        不存訊息            存訊息、排隊       處理完回 ack
```

- **Producer（生產者）**：送出訊息的一方。
- **Exchange（交換機）**：收訊息、依規則決定丟到哪些 Queue，本身**不存**訊息。
- **Queue（佇列）**：存放訊息、等 Consumer 來取的緩衝區。
- **Binding（綁定）**：Exchange 與 Queue 的連結規則，決定哪些訊息進這個 Queue。
- **Routing Key（路由鍵）**：訊息帶的字串標籤，Exchange 用它比對 Binding。
- **Consumer（消費者）**：從 Queue 取出並處理訊息的一方。

Producer 不知道訊息最後進哪個 Queue，只丟給 Exchange，由 Exchange 與 Binding 決定去向——這就是解耦。

## 四種 Exchange 類型

| 類型 | 路由行為 | 適用場景 |
| --- | --- | --- |
| `direct` | Routing Key **完全相等**才送到對應 Queue | 依明確類別分流，例如 `error` / `info` 日誌分開處理 |
| `fanout` | 忽略 Routing Key，**廣播**給所有綁定的 Queue | 一則訊息要通知很多訂閱者，例如即時推播 |
| `topic` | Routing Key 依**萬用字元**比對（`*` 一個詞、`#` 多個詞） | 依主題彈性訂閱，例如 `order.*.created` |
| `headers` | 不看 Routing Key，改比對訊息的 **header 欄位** | 需要用多個屬性組合條件路由時 |

入門最常用 `direct` 與 `fanout`。

## 範例：direct exchange 分流日誌（Python pika）

用 [pika](https://pika.readthedocs.io/) 示範一個 `direct` exchange：Producer 送出帶 `error` 或 `info` Routing Key 的日誌，Consumer 只綁 `error`，因此只收到錯誤訊息。先啟動 RabbitMQ：`docker run -d --name rabbitmq -p 5672:5672 -p 15672:15672 rabbitmq:3-management`。

```bash
pip install pika
```

**Consumer（收訊息，先跑這支）**：

```python
import pika

conn = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
channel = conn.channel()

# 宣告 exchange；durable=True 讓它在 broker 重啟後仍存在
channel.exchange_declare(exchange="logs_direct", exchange_type="direct", durable=True)

# 宣告自己要用的 queue
channel.queue_declare(queue="error_log", durable=True)

# Binding：把 queue 綁到 exchange，只收 routing_key 等於 "error" 的訊息
channel.queue_bind(exchange="logs_direct", queue="error_log", routing_key="error")

# 一次只發 1 則未 ack 的訊息，避免單一 Consumer 囤積
channel.basic_qos(prefetch_count=1)

def callback(ch, method, properties, body):
    print(f"收到 [{method.routing_key}]:", body.decode())
    # 處理完才回報 ack，RabbitMQ 這時才把訊息刪掉
    ch.basic_ack(delivery_tag=method.delivery_tag)

# auto_ack 預設為 False，代表採用手動 ack
channel.basic_consume(queue="error_log", on_message_callback=callback)

print("等待訊息，按 Ctrl+C 結束")
channel.start_consuming()
```

**Producer（送訊息）**：

```python
import pika

conn = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
channel = conn.channel()

# Producer 也宣告一次 exchange，確保它存在（參數要與 Consumer 一致）
channel.exchange_declare(exchange="logs_direct", exchange_type="direct", durable=True)

logs = [
    ("error", "磁碟空間不足"),
    ("info", "服務啟動完成"),
    ("error", "資料庫連線逾時"),
]

for severity, text in logs:
    channel.basic_publish(
        exchange="logs_direct",
        routing_key=severity,  # Exchange 用它比對 Binding
        body=text,
        properties=pika.BasicProperties(delivery_mode=2),  # 2 = persistent，訊息也持久化
    )
    print(f"已送出 [{severity}] {text}")

conn.close()
```

本例的路由長這樣：

```
Producer
   |
   +-- routing_key = "error" --+
   +-- routing_key = "info"  --+
   +-- routing_key = "error" --+
                               v
                   +-----------------------+
                   | Exchange: logs_direct |  type = direct
                   +-----------+-----------+
                               | 比對 Binding（key 完全相等才進）
              +----------------+----------------+
              | binding key = "error"           | 沒有 binding key = "info"
              v                                 v
     +------------------+                 （訊息被丟棄）
     | Queue: error_log |
     +--------+---------+
              v
          Consumer
```

Consumer 只會印出兩則 `error`；`info` 那則因為沒有任何 Queue 綁 `info`，會被 exchange 直接丟棄。想一併收 `info`，就再宣告一個 queue 並綁 `routing_key="info"`，或把同一個 queue 綁兩次（Binding 可以有多條）。

**要先跑 Consumer**：queue 與 binding 是由 Consumer 建立的，Producer 先跑的話訊息無處可去、當場消失——Exchange 本身不存訊息。

> 註：`exchange=""` 是**預設 exchange**，一種內建的 `direct` exchange，每個 queue 都自動以自己的名字綁在上面，所以 `routing_key` 填 queue 名稱就能直送。方便，但沒有路由彈性，正式用途建議自己宣告 exchange。

## ack 是什麼

**ack（acknowledgement，確認）**：Consumer 對 broker 說「這則訊息我處理完了，可以刪掉」。

訊息的生命週期是這樣：broker 把訊息推給 Consumer 後**不會馬上刪**，而是標成 **unacked（已投遞、未確認）**；等收到 ack 才真正從 Queue 移除。如果 Consumer 在 ack 之前當機或連線斷掉，broker 會把那些 unacked 訊息**重新排回 Queue**，派給其他 Consumer——訊息因此不會因為某台機器掛掉而消失。

```
  +---------+   投遞給 Consumer   +-----------+   basic_ack     從 Queue 移除
  |  Ready  | ------------------> |  Unacked  | --------------> （訊息消失）
  +---------+   （Queue 中不刪）   +-----------+
       ^                                |
       |  basic_nack(requeue=True)      |
       |  或 Consumer 斷線 / 當機        |
       +--------------------------------+
                                        |  basic_nack(requeue=False)
                                        +----------> 丟棄 / Dead Letter Queue
```

### 自動 ack 與手動 ack

| 模式 | 設定 | 行為 | 風險 |
| --- | --- | --- | --- |
| 自動 ack | `basic_consume(..., auto_ack=True)` | 訊息一送出就視為完成，立刻刪除 | Consumer 處理到一半當機，訊息就沒了（at-most-once） |
| 手動 ack | 預設（`auto_ack=False`）＋自行呼叫 `basic_ack` | 處理成功才確認 | 可能重複收到同一則（at-least-once） |

手動 ack 是**至少一次（at-least-once）**語意：Consumer 處理完但 ack 還沒送到就斷線，訊息會被重派，同一件事可能做兩次。因此 Consumer 的處理邏輯最好是**冪等（idempotent）**的，例如先用訂單編號檢查是否已處理過。

### 三個相關 API

```python
# 確認成功，刪除訊息
ch.basic_ack(delivery_tag=method.delivery_tag)

# 處理失敗：requeue=True 放回 Queue 重試
ch.basic_nack(delivery_tag=method.delivery_tag, requeue=True)

# 處理失敗且不想重試：丟棄，或轉進 dead letter exchange（若有設定）
ch.basic_nack(delivery_tag=method.delivery_tag, requeue=False)
```

`basic_reject` 與 `basic_nack` 作用相同，差別是 `basic_nack` 多了 `multiple=True`，可一次處理到某個 `delivery_tag` 為止的所有訊息。

`delivery_tag` 是 broker 在**該條 channel 內**給每則投遞的遞增編號，ack 時用它指名是哪一則；它只在這條 channel 有效，換條 channel 就不能用。

### 忘了 ack 會怎樣

訊息會永遠停在 unacked 狀態，不會被刪也不會重派。配上 `prefetch_count=1`，這個 Consumer 的額度直接被佔滿，之後**再也收不到新訊息**——看起來像整個服務卡住。在 Management UI 的 Queue 頁面看到 `Unacked` 數字一直不降，通常就是這個原因。

反過來，如果一直 `requeue=True` 重試又一直失敗，訊息會在 Queue 與 Consumer 之間無限繞圈（poison message）。實務上會設**重試次數上限**，超過就 `requeue=False` 送進 dead letter queue 另行處理。

## 持久化：重開機後訊息還在嗎

預設情況下，RabbitMQ 很多東西是**只放在記憶體**的：伺服器一重開，Queue 不見、裡面的訊息也不見。想讓它們活過重啟，要把資料寫進硬碟，這件事叫**持久化**。

麻煩的是「寫進硬碟」要分**三個**地方設定，缺一個就前功盡棄：

| 要保住什麼 | 怎麼設 | 不設的下場 |
| --- | --- | --- |
| Exchange 的存在 | `exchange_declare(..., durable=True)` | 重啟後 exchange 消失，Producer 送訊息會被拒 |
| Queue 的存在 | `queue_declare(..., durable=True)` | 重啟後 queue 連同裡面的訊息一起消失 |
| 訊息本身 | 送出時 `delivery_mode=2` | queue 還在，但裡面是空的——訊息沒被寫進硬碟 |

兩個關鍵字：

- **durable（持久的）**：形容 **Exchange 與 Queue** 這些「容器」。意思是「這個容器的定義寫進硬碟」，重啟後 RabbitMQ 會照原樣把它建回來。相對的是 `durable=False`，重啟即消失。
- **persistent（持久化的訊息）**：形容**訊息本體**。在 pika 裡就是 `delivery_mode=2`（`1` 是不寫硬碟）。

用個比喻：`durable` 是把**櫃子**釘在牆上，`persistent` 是把**文件**放進防火保險箱。櫃子釘死了但文件是影印紙，火災一樣沒東西；文件防火但櫃子沒釘，櫃子倒了也找不到。

補一句常見誤解：持久化只保證「broker 重啟後訊息還在」，不保證「訊息絕對不遺失」。訊息從送出到寫入硬碟之間有短暫空窗，這段期間 broker 掛掉仍會掉。要更保險得再開 **publisher confirms**（broker 回報「我收下並存好了」），這屬於進階主題，可看參考資料的 Confirms 文件。

## prefetch：訊息怎麼分給多個 Consumer

同一個 Queue 可以掛很多個 Consumer 分擔工作。RabbitMQ 預設用 **round-robin（輪流）** 派送：第 1 則給 A、第 2 則給 B、第 3 則又給 A……**完全不管誰現在忙不忙**。

如果訊息處理時間不平均（有的 1 秒、有的 30 秒），輪流派就會出事：倒楣的 Consumer 手上塞了一堆重活，另一個早就閒著沒事做。

`channel.basic_qos(prefetch_count=N)` 就是來修這件事的：限制**每條 channel 同時最多只能有 N 則未 ack 的訊息**，額度滿了 broker 就不再派新的給它，直到它 ack 掉一則、空出一格。

```
prefetch 未設（預設不限）：
  Queue: [7][6][5][4][3][2][1]
            |
            +--> Consumer A   拿到 1,3,5,7   <- 還在忙也照塞
            +--> Consumer B   拿到 2,4,6

prefetch_count = 1：
  Queue: [7][6][5][4][3]
            |
            +--> Consumer A   [1] 處理中（未 ack，broker 暫不再派）
            +--> Consumer B   [2] ack 完 -> 馬上拿走 [3]
```

`prefetch_count=1` 就是所謂的**公平分派（fair dispatch）**：處理完一則才拿下一則，誰快誰多做。代價是每則訊息都多一次來回等待，吞吐量會低一些。訊息處理很快（毫秒級）時，值設大一點（例如 10～100）讓 broker 先把訊息預先塞給 Consumer，避免每則都在等網路往返。

兩個前提：

- **只在手動 ack 下有意義**。`auto_ack=True` 時訊息一送出就算 ack 完，永遠不會有未 ack 訊息，prefetch 形同虛設。
- **額度是算 channel 的**，不是算連線或算 Consumer。一條 channel 開多個 Consumer 時，額度是大家共用的。

## 宣告要一致：PRECONDITION_FAILED

`exchange_declare` 與 `queue_declare` 的語意是「**確保它存在**」而不是「建立它」：不存在就建，已存在且**參數完全相同**就什麼都不做。所以 Producer 與 Consumer 兩邊都各宣告一次是慣例，誰先啟動都能跑。

但參數只要有一項對不上——`durable` 從 `True` 改成 `False`、`exchange_type` 從 `direct` 改成 `topic`、`arguments` 多加一個設定——broker 會回：

```
PRECONDITION_FAILED - inequivalent arg 'type' for exchange 'logs_direct'
```

而且不只是報錯，**整條 channel 會被關掉**，後續操作全部失敗。

已經存在的 exchange / queue **不能改參數**。要調整只有兩條路：

1. 換一個新名字宣告（最安全，舊的可以慢慢淘汰）。
2. 先刪掉舊的再重建——`channel.queue_delete(queue="error_log")`。注意**裡面沒處理完的訊息會一起消失**。

實務上把宣告參數集中寫成一份共用設定，Producer 與 Consumer 都引用同一份，比兩邊各抄一次可靠。

## Management UI：出事先看這裡

啟動指令裡的 `-p 15672:15672` 就是為了這個網頁介面：`http://localhost:15672`，預設帳密 `guest` / `guest`（`guest` 基於安全考量**只能從 localhost 登入**，遠端機器要另外建帳號）。

最常看的是 **Queues** 頁的三個數字：

| 欄位 | 意思 | 不正常時代表什麼 |
| --- | --- | --- |
| `Ready` | 排隊中、還沒送給任何 Consumer | 一直漲：Consumer 太慢或根本沒開 |
| `Unacked` | 已送出、還沒收到 ack | 高且不動：忘了 ack，或處理卡住 |
| `Total` | 前兩者相加 | 整體堆積量 |

一個常見情境：訊息送了卻沒人收，但 `Ready` 與 `Unacked` 都是 0——這表示訊息根本沒進到這個 Queue，去 **Exchanges** 頁點開該 exchange，看 Bindings 區塊的 routing key 是不是綁錯或沒綁。

其他好用的地方：

- Queue 詳細頁的 **Publish message** 可以直接手動送一則測試訊息，不用寫 Producer。
- 同頁的 **Get messages** 能偷看佇列裡的內容（注意：預設會把訊息 requeue 放回去，但順序可能被打亂，正式環境慎用）。
- 不想開瀏覽器就用 CLI：`rabbitmqctl list_queues name messages_ready messages_unacknowledged`。
