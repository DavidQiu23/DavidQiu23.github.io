同一台機器，同一支程式跑了兩份。同一份工作，同時只准一個做。呼叫端是 async。

先分清楚兩個詞，全篇的因果都靠它們：

- **行程 (process)**：一份獨立執行中的程式。跑兩份就是兩個行程，各有各的記憶體，看不到對方的變數
- **執行緒 (thread)**：一個行程裡同時做事的分身。同一行程內的執行緒共用記憶體

差別的後果：同一行程內要互斥，用程式裡的變數就辦得到；**跨行程**互斥雙方連記憶體都不共用，只能請作業系統出面，用一個雙方都叫得到的東西當信物。

跨行程互斥，第一個想到的通常是具名 `Mutex`——它本來就是為這件事設計的。

但呼叫端是 async 的話，這條路走不通，而且是執行到一半才炸。問題出在 `Mutex` 的**擁有權 (ownership)** 設計。

以下內容以 Windows 環境為前提。

{: .notice--warning}
> 這篇的做法只在**同一台機器**內有效。作業系統提供的具名物件不跨機器，同一支程式部署到兩台伺服器時，兩邊會各自取得自己那台的鎖、同時開跑——而且不會有任何錯誤訊息。跨機器互斥要換分散式鎖：資料庫的 row lock、Redis，或雲端服務提供的 lease。

## 互斥鎖 = 守門員

互斥鎖 (mutual exclusion lock) 的工作是看門：同一段程式碼，同時只准一個進去。

四個性質：

| 性質 | 白話 |
| --- | --- |
| **擁有權 (ownership)** | 鎖記主人。只有主人能開。.NET 的主人 = **執行緒**，即**執行緒親和性 (thread affinity)** |
| **可重入 (reentrancy)** | 主人可再進。數次數。數回零才真開 |
| **阻塞等待** | 拿不到 → 執行緒去睡，讓出 CPU。不空轉 |
| **作用範圍** | 行程內（`lock` / `Monitor`）；跨行程（具名 kernel 物件） |

擁有權看起來是好東西。A 上鎖 B 解鎖 → 當場抓包。可重入也靠它：要數進出次數，得先認人。

壞就壞在認的是**執行緒**。而 async 的專長就是換執行緒。

## Mutex 撞 await

C# 連試都不給試。`lock` 裡放 `await` = 編譯錯：

```csharp
lock (_gate)
{
    await DoWorkAsync();   // CS1996: Cannot await in the body of a lock statement
}
```

編譯器懂行：`await` 之後可能換執行緒，而 `Monitor` 只認原執行緒。擋你 = 救你。

改手動控制具名 `Mutex`。編譯過。執行期照炸：

```csharp
// Global\ 是全機器可見的名字，命名規則見文末〈命名與權限〉
var mutex = new Mutex(false, @"Global\MyJob");
mutex.WaitOne(0);        // 執行緒 A 取得
await DoWorkAsync();     // 續行可能換到執行緒 B
mutex.ReleaseMutex();    // 💥
```

實測：

```
取鎖執行緒 Id=1
釋放執行緒 Id=4
ApplicationException: Object synchronization method was called from an
unsynchronized block of code.
```

為什麼會換執行緒？

`await` 的意思是「這裡先讓出去，等它好了再回來接」。讓出去的那一刻，原本那條執行緒就被放回**執行緒池 (thread pool)** 去做別的事了。等完之後要接手往下跑的那段程式碼叫**續行 (continuation)**——由執行緒池另外派一條空著的執行緒來跑，不保證是原來那條。

ASP.NET Core 沒有 `SynchronizationContext`（一種「把續行送回原本那條執行緒」的機制），續行直接丟進執行緒池，換人幾乎必然。

## 解法：具名 Semaphore(1, 1)

擋路的是擁有權 → 換一個不認人的 kernel 物件。

`Semaphore` = 計數器。只數名額，不記臉。

```csharp
// 兩個 1 分別是「初始名額」與「名額上限」
var sem = new Semaphore(1, 1, @"Global\MyJob");
sem.WaitOne(0);
await DoWorkAsync();
sem.Release();           // 任何執行緒都能呼叫
```

初始名額 1 = 一開始就有一個空位可以拿；名額上限 1 = 最多也只有一個。合起來就是一把不記名的互斥鎖。

實測跨執行緒 `Release()`：

```
Semaphore 跨執行緒 Release 成功, thread=6
```

### 「沒有 WaitAsync」不等於「不能用在 async」

`Semaphore` 屬 `WaitHandle` 家族（`Mutex`、`Semaphore`、`EventWaitHandle`）。全家只有阻塞式 `WaitOne()`，沒有 `WaitAsync()`。

常見誤推：沒 `WaitAsync` → 不能用在 async。錯。兩回事。

`WaitOne(0)` = **試一下就走 (try-acquire)**。有名額 → `true`。沒有 → `false`。不等待、不阻塞。

排程要的正是這個語意：有人在跑，我跳過。也不佔執行緒池執行緒。

{: .notice--warning}
> 逾時給正值（`WaitOne(TimeSpan.FromSeconds(30))`）→ 執行緒真的被卡 30 秒。在 async 裡 = 同步阻塞。量一大 = 執行緒池飢餓 (thread starvation)。真要非同步等待 → 只剩行程內的 `SemaphoreSlim.WaitAsync()`。

包成釋放權柄：

```csharp
public static class CrossProcessLock
{
    /// <summary>取得成功回傳可 Dispose 的權柄；已被佔用則回傳 null。</summary>
    /// <param name="timeoutSeconds">
    /// 維持 0。給正值會讓這條執行緒真的卡住等待，在 async 程式裡等同同步阻塞。
    /// </param>
    public static IDisposable TryAcquire(string jobName, int timeoutSeconds = 0)
    {
        var sem = new Semaphore(1, 1, $@"Global\MyApp_Job_{jobName}");
        try
        {
            if (!sem.WaitOne(TimeSpan.FromSeconds(timeoutSeconds)))
            {
                sem.Dispose();          // 取不到就立刻關閉 handle
                return null;
            }
        }
        catch
        {
            sem.Dispose();
            throw;
        }
        return new Releaser(sem);
    }

    private sealed class Releaser : IDisposable
    {
        private Semaphore _sem;

        public Releaser(Semaphore sem) => _sem = sem;

        public void Dispose()
        {
            // 換出後置 null，避免重複 Dispose 造成多釋放一次
            var sem = Interlocked.Exchange(ref _sem, null);
            if (sem == null) return;

            sem.Release();
            sem.Dispose();
        }
    }
}
```

呼叫端：

```csharp
using var handle = CrossProcessLock.TryAcquire("NightlyReport");
if (handle == null)
{
    logger.LogWarning("另一個實例可能正在執行，本次跳過");
    return 1;
}

await RunJobAsync();     // 跨 await 沒問題
```

### 確認它真的有效

把上面兩段編成一支 console 程式，開兩個視窗，趁 A 還在跑時執行 B：

```
視窗 A：（工作正常執行中）
視窗 B：warn: 另一個實例可能正在執行，本次跳過
```

B 被擋掉 = 跨行程互斥有效。等 A 跑完再執行 B，B 應該能正常取得——這一步是在確認鎖有被正確釋放，沒有卡住不放。

## 為什麼不是別的

| 候選 | 跨行程 | 過 await | 判決 |
| --- | --- | --- | --- |
| `lock` / `Monitor` | ❌ 行程內 | ❌ 編譯就擋 | 淘汰 |
| `Mutex` | ✅ 具名 | ❌ 認執行緒 | 淘汰 |
| `SemaphoreSlim` | ❌ 純 managed | ✅ 有 `WaitAsync()` | 行程內才用 |
| `EventWaitHandle` | ✅ 具名 | ✅ 不認人 | 可用，但見下 |
| **`Semaphore(1, 1)`** | ✅ 具名 | ✅ 不認人 | **選它** |

`EventWaitHandle` 差在哪？它也能當鎖，也不認人。差別在**多釋放一次**的時候：`EventWaitHandle` 無聲無息放行，互斥從此壞掉且事後難抓；`Semaphore` 直接拋 `SemaphoreFullException`。

當場爆 > 悄悄壞。

## 代價

### 崩潰不標記 abandoned

`Mutex` 認主人，主人行程死掉時下一個等待者會收到 `AbandonedMutexException`——鎖拿得到，也知道上一手死得難看。`Semaphore` 不認人，沒這服務。

所幸 Windows 的 kernel 物件靠 **handle 引用計數**活著：最後一個 handle 關閉，物件就消失。行程崩潰時 handle 被 OS 收走，同名物件跟著蒸發，下次執行重建、計數回 1，照常取得。配上「逾時 0、拿不到立刻 `Dispose()`」，殘留視窗極小。

而且失敗的方向是安全的：取不到就拿到 `null`，走「另一個實例可能正在執行」那條路。寧可誤判忙碌而跳過，不會誤放行撞車。

### 不可重入

不認人 → 認不出「這是我自己」。同一條邏輯重複取同名鎖：逾時 0 → 自己擋自己，拿 `false`。逾時正值 → 自己鎖死自己。巢狀呼叫小心。

### 命名與權限

- `Global\` → 全機器可見，跨 session。Windows 服務要跟桌面登入的行程互斥，必用。
- `Local\`（或不加前綴）→ 只在同一登入 session 內可見。
- 名字是全機器共用的字串 → 加專案前綴，別撞名。
- 跨帳號看 ACL。服務帳號建的物件，別的帳號可能開不了（`UnauthorizedAccessException`）。.NET Core 的 `Semaphore` 建構子沒有存取控制多載 → 改用 `System.Threading.AccessControl` 套件的 `SemaphoreAcl.Create()`。

## 小結

- `Mutex` 認執行緒。`await` 換執行緒。天生不合。
- 跨行程 + async → 具名 `Semaphore(1, 1)`。不認人，誰都能 `Release()`。
- `WaitOne(0)` 不阻塞 → try-acquire 語意下，沒有 `WaitAsync()` 不是問題。逾時給正值就退回同步阻塞。
- 代價：沒 abandoned 偵測、不可重入。換到的：能跨 `await`。
